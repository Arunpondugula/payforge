# account-service

## Responsibility

`account-service` owns **identity and balance data** for PayForge. It is the single
source of truth for "who has an account, and how much recorded balance they hold."

It does **not**:
- move money between accounts (that's `ledger-service`'s responsibility, built once the
  ledger domain model and inter-service calls are wired up)
- touch card/payment data (PCI scope is deliberately narrowed to `ledger-service` only —
  see the PCI DSS scoping ADR)
- handle authentication/login (that's a separate `User` concept, introduced as part of
  the security/auth work later in the roadmap)

This mirrors how Stripe separates a `Customer`/`Account` object (identity + balance)
from `PaymentMethod` (card data) and from login/dashboard auth — different concerns,
different services, different scope.

**Important scope note:** PayForge is a *payment processing platform*, not a bank.
The `balance` field is an internal ledger record — "what PayForge's own database says
this account holds" — not a real, federally-insured deposit sitting at an actual bank.
This is the same relationship Stripe has with real banking rails: the hard engineering
problems (idempotency, ledger correctness, concurrency safety) live in this internal
ledger layer, not in real money movement, which requires actual banking partnerships
out of scope for this project.

## Database

Own Postgres schema, `accountdb`, isolated from every other service's database —
enforced at the infrastructure level (separate DB, separate credentials), not just by
convention. See `docker-compose.yml` at the repo root for the `account-db` container
definition.

| Setting | Value |
|---|---|
| Host (local dev) | `localhost:5432` |
| Database | `accountdb` |
| User | `payforgeaccount` |
| Schema management | Hibernate `ddl-auto: update` (local dev only — see note below) |

**Local-dev-only shortcut, flagged honestly:** `ddl-auto: update` auto-creates/alters
tables from entity classes. It's convenient here, but it will *never* drop a column
you've removed from an entity (a real, hit-in-practice limitation during this build —
see git history around the `firstName`/`lastName`/`contactEmail` migration). A real
production system uses versioned migrations (Flyway/Liquibase) instead, so every schema
change is reviewed, reproducible, and destructive changes are explicit and intentional.

## Entity: `Account`

| Field | Type | Notes |
|---|---|---|
| `id` | `UUID` | Primary key, client-generated (`GenerationType.UUID`). Internal, permanent, never exposed as something a human types. Used for every inter-service and DB reference. |
| `accountNumber` | `String(17)` | Human-facing reference number — `PYFORGE` + 9 random digits + 1 Luhn check digit. Generated by `AccountNumberGenerator`. Structurally self-validating (see below). |
| `firstName` / `lastName` | `String` | Structured name fields — standard practice over a single free-text name (sorting, formatting, mail-merge). |
| `contactEmail` | `String` | Notification/receipt email — **not** a login credential. Named deliberately to avoid collision with the future `User.email` (login), which arrives with the authentication work later in the roadmap. Intended future use: notification-service email delivery, alongside the existing webhook/audit consumer pattern. |
| `balance` | `BigDecimal`, `NUMERIC(19,4)` | Never `float`/`double` — floating point cannot represent decimal fractions exactly, which is unacceptable for financial data. `scale=4` allows sub-cent precision in intermediate calculations, same as real processors. |
| `currency` | `String(3)` | ISO-4217-shaped currency code. Single currency per account — a known, deliberate simplification (real Stripe accounts hold balances per currency; not built here). |
| `status` | `AccountStatus` enum (`ACTIVE`, `FROZEN`, `CLOSED`) | Stored via `@Enumerated(EnumType.STRING)`, never ordinal — storing ordinals risks silently corrupting every existing row's meaning if the enum is ever reordered. |
| `createdAt` | `Instant`, immutable (`updatable=false`) | Tamper-resistant creation timestamp. |
| `updatedAt` | `Instant` | Auto-maintained via `@PreUpdate` lifecycle callback. |
| `version` | `Long` (`@Version`) | Optimistic locking — prevents two concurrent writes from silently overwriting each other's balance changes. Directly exercised once concurrent-transfer testing is added against the ledger. |

**No public setters.** Balance is mutated only through `credit(BigDecimal)` /
`debit(BigDecimal)`, which enforce the account's own invariants (positive amounts only,
no overdraft) regardless of which layer or future service calls them. Status transitions
go through `freeze()` / `activate()` / `close()` for the same reason — the entity
protects its own state, rather than trusting every caller to do it correctly.

### Account number format

`PYFORGE` + 9 random digits + 1 Luhn check digit (17 characters total), generated and
validated by `AccountNumberGenerator` (kept as its own class — a single-responsibility
utility, separate from the `Account` entity itself, since it has nothing to do with
account *state* and needs to be reusable by other services later, e.g. `ledger-service`
validating an incoming transfer-destination account number before any DB lookup).

Uses the same Luhn algorithm as credit card numbers — a mistyped digit fails checksum
validation structurally, before any database is ever touched.

## API

Base path: `/api/v1/accounts`

### `POST /api/v1/accounts`

Creates a new account.

**Request:**
```json
{
  "firstName": "Arun",
  "lastName": "Kumar",
  "contactEmail": "arun@example.com",
  "initialBalance": 100.00,
  "currency": "USD"
}
```

**Response — `201 Created`:**
```json
{
  "id": "3f154162-af34-47ed-bbe5-8a0358db8eb0",
  "accountNumber": "PYFORGE9646690363",
  "firstName": "Arun",
  "lastName": "Kumar",
  "contactEmail": "arun@example.com",
  "balance": 100.00,
  "currency": "USD",
  "status": "ACTIVE",
  "createdAt": "2026-07-30T21:15:26.005Z"
}
```

Validation (Bean Validation via `@Valid`): `firstName`/`lastName`/`contactEmail`/`currency`
required, `contactEmail` must be email-shaped, `initialBalance` must be positive.

### `GET /api/v1/accounts/{id}`

Fetches an account by its internal UUID.

**Response — `200 OK`:** same shape as above.

**Not-found behavior — known current gap:** an unknown `id` currently returns a generic
`500`, not a `404`. This is expected at this stage — no `@ControllerAdvice` exists yet
to translate `AccountNotFoundException` into a proper HTTP status. Scheduled to be fixed
once global exception handling is added across the services.

---

## Access control — deliberate current gap, flagged for later

There is currently **no authentication** on these endpoints, and no lookup-by-account-number
endpoint exists. Both are deliberate, scoped decisions, not oversights:

- Auth arrives once the security/identity work begins (`User` entity, JWT, centralized
  validation at the Gateway).
- A public, unauthenticated "look up any account by its account number" endpoint would
  enable **account enumeration** (an attacker iterating account numbers to discover which
  are real) — a real OWASP-relevant vulnerability class, and exactly what the later
  secure-coding review is built to catch. Account-number resolution, when it's built,
  will happen server-side, as a side effect of an already-authenticated transfer request
  in `ledger-service` — never as an open lookup endpoint.

## Running locally

1. Start the database (from repo root):
   ```bash
   docker compose up -d
   ```
2. Run the service:
   ```bash
   mvn spring-boot:run
   ```
   Runs on port `8081`.
3. Verify the schema:
   ```bash
   docker exec -it payforge-account-db psql -U payforgeaccount -d accountdb -c "\d accounts"
   ```

**Build note:** the parent POM's Maven Compiler Plugin is configured with
`<parameters>true</parameters>` (the `-parameters` javac flag), so `@PathVariable`/`@RequestParam`
work correctly without explicit names. If you change parent-POM build config, run
`mvn clean install` from the repo root before restarting — a plain restart reuses
already-compiled classes and won't pick up compiler-flag changes.

## Deferred to later stages of the build (deliberate, not missing)

| Concern | Where it actually belongs |
|---|---|
| Login, JWT, `User` entity | Security/auth phase, once the Gateway centralizes JWT validation |
| KYC / verification status / business vs. individual accounts | Compliance phase (PCI DSS work) — a legitimate real-world Account concern, but scoped to that phase, not the initial scaffold |
| Card / payment method storage | `ledger-service`, added during the compliance phase — kept out of account-service specifically to narrow PCI DSS scope to one service |
| Global exception handling (`@ControllerAdvice`) | Added once account-service and ledger-service are both far enough along to share a consistent error-response shape |
| Multi-currency balances per account | Out of scope for this project — noted as a known simplification |
| Unit tests | Deliberately deferred until `ledger-service` and `notification-service` are also scaffolded, then taught as its own dedicated session |
